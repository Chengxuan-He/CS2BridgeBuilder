# Bridge Builder

![BridgeBuilder icon](assets/BridgeBuilder.svg)

A Cities: Skylines II mod that builds a **bridge prefab** from parts you choose: a road for the upper
deck, a bridge style to wear, and optionally something hung underneath.

Read about [available inputs](#what-you-can-pick), [using the builder](#in-game-builder-and-identity),
the [generation flow](#generation-flow), [technical details](#geometry-calculation), or
[building and contributing](#building).

## What you can pick

Each bridge style binds to a single content source for both display and generation. Base-game
variants take precedence over DLC variants, then mod variants; ties use stable source identifiers,
not translated labels. A selected unavailable prerequisite does not trigger a fallback to another
owner. The V-pylon double-deck cable-stayed bridge (`Extradosed01`) accepts base-game variants only,
never the duplicate Bridge Expansion Pack version. Existing bridge assets are unchanged.

The DLC landmark `GoldenGate` supports **single-deck generation only**. The separate Bridge Expansion
Pack style `GoldenGateDouble` uses its own double-deck archetype. Preview/export/create requests must
respect each style's supported arrangement. Existing saved bridges are not reconstructed by this rule.

Road Builder is **optional compatibility, not a required dependency**. Without it installed and
successfully loaded in the current playset, its roads are omitted from both deck selectors. Base-game
roads, pedestrian paths and tracks remain available. Cached Road Builder prefabs do not enable the
integration; standalone plain-road exports remain ordinary roads. The mod does not load or ship
RoadBuilder.dll, and Road Builder must not be declared a mandatory dependency when publishing it.

The upper and lower deck are chosen from everything registered in the loaded world:

| Kind | What it covers |
|---|---|
| Road Builder | roads generated by Road Builder, with their configuration still attached |
| Road | every other road — the game's own, a pack's, or one exported earlier by either mod |
| Train / Subway / Tram | the rail, subway and tram tracks |

Each entry is labelled with its kind, its in-game name and its measured width, because the width is
what decides which variant of the chosen style will fit.

Both deck selectors accept the supported network kinds above. Generation still requires a matching
bridge archetype and valid network data. Leaving the lower deck empty selects a single-deck bridge;
choosing the same road for both creates two independent deck networks.

**Bridges are never offered as decks.** A bridge already carries its own span behaviour, towers and
pillars; draping a second bridge over that gives two structures fighting for the same space. It also
keeps a generated bridge out of the list it came from, which would otherwise let one run's output
become the next run's input and compound the error each time. For the same reason a generated bridge
is not offered as a *style* donor either.

## Bridge styles

Styles use stable IDs and localized labels. Discovery binds installed prototype variants, while
explicit generator admission determines which styles and deck arrangements can be created.
The runtime catalogue omits unavailable styles; discovering a prototype does not add support for it.

The router includes all ten Bridges & Ports movable styles: Draw01–Draw03, Lift01–Lift05
and PedestrianDraw01/02. Registered styles use the same catalogue and operation behavior;
missing native prerequisites still prevent generation. Routing and compilation do not establish
human acceptance of every selected road, motion cycle, LOD or independent cold load.
See the [implementation record](docs/Movable-Bridges-Implementation.md) for per-style evidence
and [prepared materials](docs/Prepared-Materials.md) for unfinished material migration.

Generated towers, cables and LODs are private derived assets owned by the bridge. Required native
game/DLC resources remain prerequisites; external non-built-in dependencies are persisted as
byte-identical copies with original CIDs under the bridge's UUID directory.

## Double decks

Double decks use the matching archetype's `AuxiliaryNets` arrangement. The main network may be the
upper or lower deck; ownership does not determine its physical height. Deck separation and placement
come from the archetype and are not adjustable. The lower-deck direction toggle changes the selected
network's direction while preserving that arrangement. A style without a matching double-deck
archetype is refused.

Each generated deck has its own bridge-owned network copy. The auxiliary is placed with its carrier;
its independent editing and connections remain subject to the game's auxiliary-network behavior.

## In-game builder and identity

The floating BridgeBuilder button opens the runtime builder in a loaded game. Roads are shown as
icon-and-name cards (three per row); double-deck mode provides independent upper and lower network
lists. Bridge styles are likewise selected from prototype cards, and unavailable styles are omitted
when their providing DLC or mod is not installed. Creating a bridge publishes it into the running
prefab world. Create-and-build also activates the ordinary network construction tool; neither action
places a bridge automatically.

Every bridge created there has two deliberately separate names:

- `PrefabName`: immutable `b<UUID>` identity, for example
  `b6f9619ff-8b86-d011-b42d-00c04fc964ff`. Saved references, activation and deletion use only this key.
- registration name: the editable name shown in game. It can be duplicated or renamed without
  changing the prefab identity or reconstructing the bridge.

Movable bridge names use the silhouette of the complete native span, towers and lifting arms.
The native closed-pose meshes distinguish the following styles. The catalog translates these labels;
existing bridges keep their saved display names and stable style IDs.

| Bascule bridges | Lift bridges | Pedestrian bascule bridges |
| --- | --- | --- |
| Curved-Soffit Girder Bascule Bridge | Portal-Frame Lift Bridge | Fan-Cable Pedestrian Bascule Bridge |
| Solid-Web Girder Bascule Bridge | Curved-Chord Truss Lift Bridge | Overhead-Beam Pedestrian Bascule Bridge |
| Deck-Truss Bascule Bridge | Double-Deck Lift Bridge | |
| | Straight-Tower Truss Lift Bridge | |
| | Curved-Brace Tower Lift Bridge | |

The management tab lists these bridges and supports activation, display-name changes and deletion.
Construction inputs are read-only after creation; changing them means creating another UUID-backed
bridge. Confirm deletion in the management tab to remove that bridge and its placed instances.
The settings action **Remove all bridges** applies the same operation to every immediate
`ImportedData/b<UUID>/` directory. Both actions finish in the same game session. Cleanup waits for
saving and native readers, unregisters the selected owner's assets, then recursively deletes its
directory. Success requires the directory and its registrations to be gone. Independent copies in
other bridges stay in their own directories.

It is the parallel of [Road Prefab Exporter](../CS2RoadPrefabExporter) and shares its code — see
[Layout](#layout).

## One bridge at a time

There is no batch mode, and that is not a simplification of one. A bridge is a **pairing** — this
deck on top, that one underneath, in this style — and a pairing does not distribute over a list of
roads. So the page asks for the two decks explicitly and builds exactly one bridge. The road exporter
next door remains the batch tool.

## Naming and repeated creation

The runtime builder and legacy options page use the same creation path. Each creation allocates a
new immutable `b<UUID>` identity, including when the selected roads and style match an existing
bridge. A suggested display name describes the pairing; it is not an overwrite key. Renaming or
switching language does not change asset identity or saved references.

## Reports

Every run writes `ModsData\BridgeBuilder\last-export-report.txt`, including the structural
counts that separate "the deck came out wrong" from "the style did not attach": sections, overhead
sections, sub-objects and auxiliary nets. Generation and preview failures are recorded with their underlying diagnostics and shown
through localized operation-failure dialogs. The preview frame remains text-free; deletion
failures retain their operation diagnostics.

The log line `Bridge styles: N of M available, from D donor prefab(s) out of K bridge-capable
prefab(s)`, followed by one line per style, is the authoritative record of what discovery bound.

## Generation flow

All 30 generator routes (20 fixed and 10 movable styles) share the request lifecycle below.
Each selected network uses its elevated branch throughout generation; a double-deck bridge keeps
one context for each selected network and follows the archetype's main/auxiliary arrangement.
Fixed bridges retain the selected native road materials. Movable bridges also compose the road,
mechanism and corresponding materials by physical part across all LODs.

```mermaid
flowchart TD
    Request["Panel selection or queued Create request"] --> Kind{"Request kind"}
    Kind -->|Existing bridge preview| Borrow["Borrow saved prefab graph by identity"]
    Kind -->|New preview or Create| Files["Worker: read and hash requested style files"]
    Files --> Resume["OnUpdate: completed snapshot resumes main thread"]
    Resume --> Identity{"New preview or Create"}
    Identity -->|Preview| Temp["Temporary preview identity"]
    Identity -->|Create| Owner["Reserve new owner UUID"]
    Temp --> Context["Resolve elevated context once per selected network"]
    Owner --> Context
    Context --> Compose["Clone and run style generator; assemble all LODs"]
    Compose --> Result{"Preview or permanent result"}
    Result -->|Preview| Private["Retain private result and captured road context"]
    Borrow --> Render["Build preview scene and render current revision"]
    Private --> Render
    Result -->|Create| Save["Save owned prefab graph; persist native dependencies"]
    Save --> Register["Register prefabs; await scheduled native initialization"]
    Register --> Ready{"Native initialization ready"}
    Ready -->|Yes| Commit["Commit asset metadata and record export"]
    Commit --> UI["Refresh catalogue; optionally activate placement tool"]
    Ready -->|No| Failed["Report failure; defer owner recovery to restart"]
```

Create allocates its new UUID before generation and always builds again; it never commits a
preview graph. Background preparation covers file I/O and hashing, not Unity/native registration
or the entire geometry pipeline. Superseded previews release private resources. Failed permanent
creation follows owner-scoped recovery on restart rather than deleting live or healthy assets.
Structural or appearance quality does not block a player's generation choice; real input,
file and native-operation failures still report errors. Native initialization and offline checks
do not establish in-game visual correctness.

See the [bridge generation workflow design](docs/Bridge-Generation-Workflow.md#end-to-end-generation-flow)
for scheduling, thread boundaries, persistence order, cancellation and cleanup.

### What generation actually builds

```mermaid
flowchart TD
    Context["Resolve one elevated context per selected network"] --> Measure["Measure road and footways; choose prototype arrangement"]
    Measure --> Clone["Clone main network; clone auxiliary now if the mechanism needs both"]
    Clone --> Family{"Fixed or movable style"}
    Family -->|Fixed| Fixed["Select measured variant; apply native behavior; derive overhead parts, props and fitted towers at every LOD"]
    Family -->|Movable| Sample["Sample actual road, lanes and source materials in the closed pose"]
    Sample --> Bind["For each LOD: assign physical bones and appearance parts"]
    Bind --> Match{"Actual source and prototype part correspond"}
    Match -->|Yes| Material["Bind measured original-density PBR and UV mapping; use prepared resources where available"]
    Match -->|No| Original["Retain Original through its supported native representation"]
    Material --> Structure["Apply measured structural memberships, coordinate transforms, frames and face recipes"]
    Original --> Structure
    Structure --> Render["Build native structure, road and lane models; group complete LODs with stable part ownership"]
    Render --> Mechanism["Assemble skeleton, supports, moving objects, fixed bases and network sections; attach intended paint"]
    Mechanism --> Auxiliary["Verify coordinated auxiliary or attach requested second deck"]
    Fixed --> Auxiliary
    Auxiliary --> Result["Collect owned graph: temporary preview or permanent save and publication"]
```

The fixed and movable branches do different work: fixed roads keep their native surfaces and
markings; movable roads are sampled and matched by actual physical part, not a bridge-wide
material override. Known geometry memberships and prepared material units are authored offline.
Runtime applies those measurements to the chosen road, binds original or prepared resources,
and only uses conditional runtime conversion where the material contract permits it. It does
not bake the entire bridge into a new texture. Source geometry, frames, UVs and bones follow the
recorded transform/face recipes; all LODs are assembled before native publication.

The diagram summarizes a shared sequence, not identical part recipes for every style. Combined
physical/appearance partitioning, fixed versus moving receivers, coordinated double decks and
style-specific paint/support assembly are expanded in the workflow design:
[generation core](docs/Bridge-Generation-Workflow.md#generation-core-actual-sequence-and-branches),
[movable workflow](docs/Bridge-Generation-Workflow.md#movable-generation-sampling-geometry-and-material-realization)
and [offline/runtime products](docs/Bridge-Generation-Workflow.md#offline-inputs-and-runtime-products).
Actual unavailable inputs or failed data/native operations exit to the failure lifecycle above;
structural appearance is not an added rejection stage.

## Geometry calculation

Bridge geometry uses measured affine coefficients for X, Y and Z, stored in DLL-embedded
typed arrays and compact part recipes. Independent numerical batches and movable LOD plans
run on the CPU through `AffineGeometry`; native mesh access, materials and asset persistence
remain on the main thread. Small batches execute serially to avoid scheduling overhead.
This changes generation-time computation, not the runtime requirements of saved bridges.
See the [affine execution contract](docs/agent-contract/BRIDGE_GENERATION_CONTRACT.md#cpu-affine-geometry-execution)
and [contributor workflow](docs/Adding-Bridge-Styles-With-Coding-Agents.md#affine-matrix-generation-step).
End-to-end speed improvements require in-game measurements.

### Width

Generation selects a compatible prototype variant and uses its measured geometry data. Authored
parts reaching or crossing the centre line stretch against their own span; side parts translate
rigidly, subject to the documented complete-assembly rules for Lift01 and Lift02. The same
classification applies to every LOD. Actual missing inputs are reported; structural quality or a
finite zero/reversed width does not block generation or select an arbitrary replacement design.

The [material contract](docs/agent-contract/MATERIAL_GENERATION_CONTRACT.md#2-preserve-source-resolution-and-pattern-scale)
allows verified non-tiling structural UV mappings to stretch with that geometry while retaining
authored UVs, original textures, resolution, channels, mips and compatible material identity.
This does not apply to processed movable-road materials: those use original-density tiling,
physical-part correspondence and removal of embedded road markings across all LODs.
Tiling mappings retain original physical density. Evidence must identify the source, part, LOD
and affected axes; a failed mapping or missing repeat evidence does not qualify. Selected-road
appearance and marking layout retain their existing rules. This permission is not an implementation
or visual-acceptance claim.

## What the composer does not touch

Preserve the selected road's lane layout, upgrade alternatives and native semantics. Fixed
bridge composition retains unchanged section references; movable generation derives the
necessary section conditions and visible object geometry under the movable contract.

An earlier version also appended the donor's elevated-only sections, to pick up the deck edges. That
is the one operation that changes how the net tiles across its own width — the composition system
lays sections side by side and computes their offsets, so sections authored for a different net at a
different width are not decoration but a second, conflicting layout. Everything the composer still
copies is additive: drawn above the deck, or anchored alongside it.

Fixed spans are copied only when the deck has sections that respond to the states they set. A fixed
segment declares "this span is N metres and sets state X"; the sections that answer X stay with the
donor, so copying the declaration alone lays the structure out around a main span that is never
built - which is what "placed, but the parts did not join up" looks like. Deck props anchored to a
fixed span go with them: `m_FixedIndex` is read by a compiled job with no bounds check, so an index
past the end of the array is not an exception but a hard crash.

Donor selection ranks by kind before width: a road deck prefers a road donor over a track one, and a
single-deck bridge prefers a single-deck donor. Width alone once picked a double-deck *train* bridge
to drape over a road, because it happened to be the closest match in metres.

### Geometry fitting

Every style routes to its own generator. Towers, cable pieces and LODs are private derived assets
owned by the generated bridge. The selected road supplies its network structure; bridge behavior,
components, materials and placement follow the matching archetype.

Recorded authored parts that reach the centre line stretch across their own span. Side parts move
rigidly by half the width change. Full-detail geometry and every LOD use the same part classification.
Missing supported metadata is a generation failure, not permission to guess a different bridge.
Game assets and derived content remain subject to their original licenses.

## Bridge persistence

Saved bridges use native game assets grouped by their immutable `b<UUID>` owner under
`%USERPROFILE%\AppData\LocalLow\Colossal Order\Cities Skylines II\ImportedData\`.
The following tree shows the layout; appearance, cache and dependency entries are created
only when needed, and filenames other than `Bridge.Prefab` are illustrative.

```text
ImportedData/
└── b<UUID>/
    ├── Prefabs/
    │   ├── Bridge.Prefab             Main bridge network
    │   ├── Bridge.Prefab.cid         Native asset identity
    │   └── <part or LOD>.Prefab      Other owned network/render components
    ├── Geometry/
    │   └── <mesh or LOD>.Geometry    Private generated geometry
    ├── Appearance/
    │   ├── <name>.Surface           Owned material data
    │   ├── <name>.Texture           Owned texture data
    │   ├── VT/
    │   │   └── <name>.VTTexture     Owned virtual-texture payloads
    │   └── MidMips/
    │       └── <cacheCID>/
    │           └── TS512_MB3.MidMips
    ├── Locales/
    │   └── en-US.loc                Native names/descriptions; other locales alongside
    ├── Dependencies/
    │   ├── <CID>.Surface            Unchanged external dependency snapshots
    │   ├── <CID>.Texture
    │   └── <cacheCID>/
    │       └── TS512_MB3.MidMips
    └── BridgeCacheEdges.txt         Forward cache relations for later self-checks
```

Every native asset payload has a matching `.cid` sidecar, omitted from most tree entries
for readability. Cache filenames preserve their native `TS…_MB….MidMips` tag; the shown
tag is an example. `Appearance` may also contain `.Material` files, and `VT` may contain
`.VTSurface` files. `BridgeCacheEdges.txt` is manager metadata, not a native asset or a
separate bridge registry.

Generated components and geometry have private identities. Required external non-built-in
dependencies are copied byte-for-byte with their original CIDs, once per bridge; different
bridges keep independent copies. Built-in game/DLC assets remain native references and
must remain available. Persistence follows exact dependency CIDs and declared cache edges,
without building a global asset or MidMips index.

See the [persistence policy](docs/Bridge-Asset-Persistence.md) for naming and migration rules,
and the [implementation overview](docs/Dependency-Persistence-Implementation.md) for lookup
and self-check behavior.

## Creation durability and recovery

Creation reserves a UUID in memory and stores incomplete-creation metadata on the bridge root asset.
The catalogue commits the bridge after native publication succeeds. Bridge metadata is asset-local;
there is no separate bridge registry file or registration guard rejecting native loads.

Startup self-check waits for native loading, mod initialization and PDX asset batches. It attempts
migration first, preserving UUID/CID and valid data. An unresolved shadowed CID or unverifiable
cache relation leaves inspection unfinished. Confirmed failed or impossible migration enters UUID-scoped
backup/removal; backup failure falls back to deleting the remaining selected source files. Actual
removal failures are reported. Persistent changes require restart; self-check does not unregister
live prefabs. See contract sections 17–19 for persistence, ownership and migration requirements.

## Building

```powershell
tools\Build.ps1
```

```powershell
tools\Install.ps1
```

`Build.ps1` compiles the checked-in source snapshot at `vendor/CS2ModShared/src` and verifies its
SHA-256 manifest with `tools/CheckSharedSources.ps1`. A sibling repository is not needed. The script
resolves the installed game assemblies; pass `-GameDir` to override. Game assemblies and the .NET SDK
are still external build prerequisites; the shared snapshot alone does not pin those versions.

## Layout

```
CS2ModShared/               shared - discovery, cloning, asset IO, speed-limit correction, status model
CS2RoadPrefabExporter/      exports Road Builder roads as plain roads, in batches
CS2BridgeBuilder/            this repository
```

The shared code is **compiled into** each mod rather than referenced as an assembly: its types are
`internal`, and a CS2 mod ships as a single DLL. The one thing it needs from its host — an id, a log,
a page-rebuild callback and the export naming policy — comes through `ModHost`.

The sibling projects describe the source family. This checkout builds from its own reviewed snapshot; see `vendor/CS2ModShared/README.md` for update instructions.

### Source layout and checks

`BridgeGenerationSystem` is split into lifecycle/catalogue, composition, preview, management
and removal partial files. Source-policy checks read all these files together.

Non-visual checks include `tools/AssetMetadataCheck`, `tools/DependencyCopyCheck`,
`tools/DependencySourceCheck`, `tools/SelfCheckLifecycleCheck`, `tools/DiskAuditCheck`,
`tools/PublicationCheck`, and `tools/Check*.mjs` (UI,
localization and source policy). Preview/generation failures use localized failure dialogs
and ERROR diagnostics; the preview itself has no inline error footer. Deletion failures
retain their operation diagnostics.

These checks and a successful build do not establish in-game visual correctness or save compatibility.

## Adding a bridge style with a coding agent

This guide helps contributors extend Bridge Builder with a measured bridge archetype. A new style
requires a working generator, compatible persisted assets and human in-game acceptance; adding a
catalogue entry alone is not sufficient. You provide the design and test it in game; your coding

#### Affine matrix generation step

Use the [CPU affine execution contract](docs/agent-contract/BRIDGE_GENERATION_CONTRACT.md#cpu-affine-geometry-execution)
for every style's coordinate stage:

1. Extract measured origins, coefficient rows, parameter domains and part membership offline.
   Each of X, Y and Z may depend on width; a constant axis has zero coefficients.
2. Store numerical values in the existing DLL-embedded typed arrays. Sparse vertex weights and
   part ranges are valid matrix representations; the BBN1 format need not change or expand to
   dense matrices. Preserve float bits, anchors and evaluation order.
3. Load only demanded binary resources into the current generation's parameter session. Reuse
   decoded arrays, membership records and SIMD programs within that request and its joined LOD
   workers. Release references on completion, failure or cancellation; no catalogue preload,
   permanent static parameter arrays or forced garbage collection.
4. Snapshot native inputs on the main thread. `AffineGeometry.Execute` consumes offline APF2
   stages with actual interleaved `x0,y0,z0,x1,...` storage. Load/bind operands, execute ordered
   SIMD operations, and store/scatter results with unchanged-axis masks and alias snapshots.
   Expression-recognition paths and per-axis register columns are prohibited. Scalar coefficient
   and frame programs remain distinct from vertex storage.
5. `Groups` joins independent LOD plans before main-thread native construction. Offline row-dependency
   proof permits bounded blocks; dependent stages keep their order. Native position bytes consume
   the completed owned array directly, without scalar XYZ repacking. Later preview/publication
   must not retain parameter sessions or borrowed parameter arrays.
6. Run the [offline lowering pass](tools/AffineGeometryMigration/README.md), resource/lifetime guards,
   numerical/LOD checks and localization checks after regeneration. Report initial checksum/decode
   separately from within-request cached execution. Measure preparation, operand loads, arithmetic,
   output stores and final byte copy separately before claiming an acceleration; arithmetic stages
   include memory traffic, not just pure ALU work.

The implementation entry points are [AffineGeometry.cs](src/BridgeBuilder/Bridges/AffineGeometry.cs),
[HardcodedNumbers.cs](src/BridgeBuilder/Bridges/HardcodedNumbers.cs) and
[MovableRenderAssembly.cs](src/BridgeBuilder/Bridges/Common/Movable/MovableRenderAssembly.cs).
This stage changes computation only: preserve topology, native bone ownership, material/UV
semantics and independent asset persistence.

### 4. Measure geometry before implementing transforms

Identify authored parts offline using the highest-detail prototype. Record exact mesh/LOD identity
and part membership as immutable data; runtime code consumes this data without rediscovering parts
from bounds, topology, thresholds or name resemblance.

- Apply contract section 8's explicit base, centred-post and Draw03 truss rules and section 5's
  measured Golden mappings; otherwise a part
  reaching or crossing `x = 0` stretches against its own span and a side part translates rigidly.
- Preserve tower height/depth outside the measured Golden ornament exception, side-part thickness
  and native behavior. Apply only the contracts' scoped topology, native representation and
  UV/material rules, including the verified prototype non-tiling exception.
- Carry the highest-detail classification to all LODs. Repoint derived LOD references to derived meshes.
- Preserve prototype placement, stacking, tiling, lights and their parent relationships.
- Apply the contract's separate base and pier rules using structural evidence, not names.
- Derive a double-deck style from a real double-deck prototype; retain its separation and orientation.

Consult existing metaprogram modes in `tools/GeometryMetaprogram/Program.cs`; there is no universal
command that measures and implements an arbitrary style automatically. Do not change a generated
table without retaining the source evidence and documenting how to reproduce it.

For the width audit, compare a real prototype with a real newly generated bridge. Measure complete
left-to-right spans (`maxX - minX`) on the same basis. Ask your agent to perform and document the
required width calculation using the project's binary32 rules.
The human creates the sample. A missing sample means the audit is incomplete, and a discrepancy
outside the contract's allowed range needs investigation rather than a guessed correction.

### 5. Keep persistence compatible

Use the existing naming, layout and native persistence helpers. Bridge asset ownership is determined
by `b{uuid}` in the path, not metadata. Generated components must carry their bridge UUID. Do not
truncate it or invent a separate registration store.

External dependency snapshots retain original bytes and CIDs, deduplicated within one bridge and
stored separately for different bridges. Stop traversal at built-in resources. Never select another
Bridge Builder bridge's Prefab from `ImportedData`, even if its CID matches and its file is readable.
Use original or otherwise permitted sources and fail explicitly if none is available.

Persist native unlock conditions, prices, names, descriptions and icons. Do not save Bridge Builder
component types, custom UI-host requirements or third-party editor-only components as runtime
requirements. Preserve native pricing rather than introducing price-only copies or runtime overrides.
The known double-deck rail-seam compatibility limitation still requires explicit testing and disclosure.

If a style change affects existing assets, trace self-check migration as well. Complete missing fields
individually, preserve bridge/deck UUID and CID, and use the same layout as new generation. Successful
migration must be idempotent. Failed migration follows the contract's backup/move and deletion fallback;
do not use self-check to unregister live Prefabs. Persistent migration requires a restart.

### 6. Build, deploy and verify

From the repository root, the build entry point is:

```powershell
.\tools\Build.ps1 -Configuration Release
```

Use `-GameDir` if automatic game discovery does not find the installation. Follow contract section 13
for shutdown, backup, recovery and installation. Preserve healthy bridges when generation code
changes. Only a demonstrated incompatibility permits recovery of the affected style/UUID-owned
assets; preserve unrelated bridges and dependencies. Trace shared-code impacts before recovery.

If bridge-generation code did not change, remove no existing bridges. Documentation-only edits
require no shutdown, cleanup, build or deployment. Preserve diagnostic evidence before scoped cleanup
and verify both removal of selected assets and retention of unaffected assets. Verify installed files
against the build output. Deployment does not authorize publishing to GitHub or Paradox Mods.

Run relevant existing nonvisual checks for naming, source selection, persistence, localization,
unlocking and native pricing when those paths change. Unit tests do not validate visual geometry and
must not replace the contract's human near/far inspection. Do not add tests that merely duplicate the
implementation or claim a build proves appearance.

Test the following in your local game and give the results to your agent:

1. The intended style is discoverable with required native content and packaged resources available.
   Players need not own identical original prototype files; missing required resources fail explicitly.
2. Creation and placement work at prototype and wider widths, including supported asymmetric
   roads and both deck directions. Movable bridges have no special narrow-road adaptation gate.
3. Towers, deck, cables, railings, lights and materials remain correct up close and through LOD changes.
4. Native unlock conditions, construction cost, labels, descriptions and icons are correct.
5. Saving, exiting and cold-start loading preserve geometry and references; healthy self-check is inert.
6. With Bridge Builder disabled, persisted bridges remain available and usable; retain required native
   game/DLC resources. Separately test any known rail-seam limitation.
7. When applicable, legacy migration preserves identity and a second check makes no further changes.

### 7. When the generated bridge does not match your expectations

Tell your agent what you expected, what actually happened and how to reproduce it. Identify the
affected part rather than saying only "the bridge looks wrong." For example: "The right tower leg
becomes thicker on a wider road; it should move outward without changing thickness." Describe the
observation without assuming its cause.

Attach a screenshot of the prototype and a comparable screenshot of the generated bridge. For an
LOD issue, include both near and far views. Provide the selected road or track, deck mode, width,
elevation, bridge UUID if known, and whether the problem occurs immediately or only after reloading.
Include the relevant log and export report if available; a visual defect can occur without a logged
error. Save your city before requesting another code change, because deployment stops the game before replacing loaded binaries.

Use this follow-up prompt:

```text
The generated <style ID> bridge does not match the expected result.
Prototype: <exact Prefab name>.
Source and version: <base game + game version / DLC name + game version /
Paradox Mods ID + mod name + mod version + game version>.
Contribution branch: bridge/<bridge-name>.

Expected: <describe the correct appearance or behavior of the affected part>.
Actual: <describe the difference, including which side, part or viewing distance is affected>.
Steps to reproduce: <selected road/track, deck mode, width, elevation and placement steps>.
Timing: <immediately after creation / after save and reload / after a cold start>.
Evidence: <prototype and generated screenshots, logs, export report and bridge UUID if available>.
Last working result, if known: <build/commit and what changed since then>.

Compare the generated bridge with this exact prototype and identify the cause from evidence.
Check the affected components, references, materials and all LODs; do not guess a geometric
correction or borrow another style's measurements. Preserve unrelated working behavior and
existing bridge identities. Implement the smallest justified fix, check affected callers,
build and install it locally, and explain what I should retest in game.
If evidence is missing, tell me exactly which screenshot, log or measurement you need.
Do not publish a release or push to GitHub. I will verify the local result.
```

After testing the next build, report whether the same reproduction steps now pass and attach new
screenshots. If the defect persists, explicitly say it is the same issue and retain the previous
evidence so your agent can compare attempts instead of repeating an unsupported explanation.

### 8. Deliver locally; optionally submit a GitHub pull request

Deliver a reviewed local working tree or patch with the evidence and verification summary below.
No GitHub account, upload or pull request is required to complete development.

If you explicitly choose GitHub contribution and have permission to publish to your fork, you may
upload the contribution branch and open a pull request. The following commands are optional, not
automatic agent actions; stage only files belonging to the contribution:

```powershell
git commit -m "Add stone arch bridge style"
git push -u origin bridge/stone-arch
```

In GitHub, select your fork's `bridge/stone-arch` as the compare branch. Select the upstream target
branch requested by the maintainers; if none has been specified, use the repository's default branch.
Do not push changes to every upstream branch or upload a release to Paradox Mods. Maintainers review,
merge and publish accepted contributions.

Include the following in the local handoff or optional pull request:

- The bridge style and supported deck modes, with required DLC or source assets.
- A short explanation of the implementation and any shared code it changes.
- Prototype measurements and reproducible evidence, without redistributing assets you lack permission to share.
- Near/far screenshots and results for creation, save/load and cold-start testing.
- Build and nonvisual checks actually completed, plus known limitations and unfinished checks.
- Any effect on existing bridges and how migration preserves their identity.

Have your agent help summarize the changes, but review the code and verify its claims before
delivery. A successful build is not evidence that a bridge looks correct or survives a restart.
Address review feedback locally; update a remote pull request only if that optional workflow was chosen.
