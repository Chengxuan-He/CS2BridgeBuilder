## Exact numeric contract

The audit executes only these two formulae:

```text
widthIncrement =
    (archetypeBridgeX - archetypeRoadX)
    - (generatedBridgeX - generatedRoadX)

newBridgeX = generatedBridgeX + widthIncrement
```

`BridgeX` and `RoadX` are the positive one-sided x boundaries. This makes `widthIncrement` the x
coordinate correction to apply at each side and makes the `1 m` threshold a coordinate threshold,
not a full-span threshold.

Every source token is parsed directly as IEEE-754 binary32 (`System.Single`). Every subtraction and
addition above is performed on binary32 locals in the written order. The output uses round-trip `R`
text and records the raw hexadecimal bit pattern. There is no decimal arithmetic, display-value
reuse, rounding, tolerance, epsilon, forced zero or special-case result.

A bridge is skipped if and only if:

```text
abs(widthIncrement) > 1.0f
```

Positive zero is unchanged only when its raw bit pattern is exactly `0x00000000`. Any other
non-skipped bit pattern is an applicable correction.

retained generated prefab's actual authored-width bits and would violate the bitwise requirement.

## Measurement selection

Road boundaries are the sum of the real prefab's ordinary top-level road-section allocations. An
optional section requiring another network state is not added to the straight-run road, and an
outward `Side` blend is not carriageway. Bridge boundaries are selected by reviewed source identities
in the metaprogramming audit:

- `Overhead`: half of the authored width of the selected overhead net section.
- `Object`: the exact outer x bound of the named bridge structural object and its authored
  replacement meshes.
- `Outer`: the greater of those two measured boundaries.

The identities are explicit in `tools\AuditBridgeWidths.ps1`. No running-game geometry guess,
nominal road width, rounded `tower-measurements.txt` value, or current generator formula is used as
an audit input.
