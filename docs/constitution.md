# Project constitution

This document is normative within its stated scope. Responsibility-based placement does not
change requirement strength, existing specialist exceptions or explicit user authorizations.
Specifications are equally normative; this separation introduces no new precedence hierarchy.

## Native persistence and portable paths

All project data files must use existing file extensions rather than inventing project-specific
file extensions. Prefer Cities: Skylines II file extensions and supported serialization APIs for game
assets; established general-purpose file extensions are also permitted even when the game does not
use them. Empty placeholder files are exempt. This applies to source data, build inputs, embedded
resources and runtime-persisted data. Established binary file extensions permit compact
application-specific layouts without conversion to another extension. Numerical storage details
are maintained in the [numerical-resource design](specs/generation-spec.md).
All configuration files must use `.json`. Migrate existing `.ini` configuration to `.json`, preserving
its meaning and user values. Existing general-purpose non-configuration data does not require
conversion merely because the game uses a different serialization API.
Game-native asset implementations may differ from Unity-native implementations; establish the
actual game reader and writer before selecting a game asset representation. Previously published
runtime layouts are migrated only by self-check before normal consumers access the current data.

Paths supplied by the project must be relative or explicitly supplied by the user. Resolve relative
paths against the appropriate game-provided, installation or project root at the IO boundary;
absolute paths returned by platform/game APIs are runtime resolution results, not hardcoded defaults.
Do not hardcode developer drive letters, user profiles or workspace locations. Release binaries,
symbols and distributed resources must not embed developer workspace paths. Build tools must map
source paths to portable relative names and verify the distributed artifacts, not just source text.

## Backward and cross-environment compatibility

Development, fixes and refactoring must consider backward compatibility with bridges generated by
previously published Bridge Builder versions, their existing saves, persisted formats, asset identities
and references. Unpublished development builds and experimental intermediate formats are outside
the required backward-compatibility scope. Establish release provenance before retaining a legacy
format adapter; do not infer publication from a local version label alone.
Backward compatibility is implemented exclusively by self-check migration from previously
published formats to the current format. Normal generation, loading, preview, rendering and UI
consume only the current Bridge Builder format; they must not retain old-version adapters.
Preserve healthy content and identities through persistent migration before normal use, subject to the scoped exception below.

Legacy bridges using Bridge Builder owner-persisted custom shader programs are explicitly outside backward compatibility, including previously published versions. Self-check alone identifies this obsolete protocol from concrete owned program payloads or serialized legacy program/template references and removes the affected owner through its existing backup/removal and restart flow. Do not migrate, restore or reinterpret those programs. Age, style, a missing mod program or an unrelated shader error is not sufficient evidence. Healthy noncustom bridges retain the ordinary additive migration and preservation policy. This exception grants no deletion authority to generation, preview, loading, export or UI operations.
This does not promise compatibility
with every older game API or remove the requirement to keep Bridge Builder enabled for its runtime
program registration.

Cross-environment compatibility is a design and review obligation, not an assumption based on one
machine. Consider differing operating systems, graphics vendors, cloud execution, filesystem
permissions, directory mappings, compilers, runtimes and architectures under the
[required environment matrix](specs/cross-environment-spec.md#cross-environment-3-required-matrix-and-evidence-limits).
A candidate environment is not automatically a supported or verified host.
CUDA use is prohibited throughout the project; users cannot be assumed to have an NVIDIA GPU.
Directory mappings must not be prohibited or treated as a reason to reject an otherwise valid
operation. Users may map directories to avoid system-drive growth or for other purposes. Mapped
and unmapped directories must have identical observable behavior for equivalent inputs, permissions
and storage availability, including persistence, backup and removal.
Every agent must read the complete [cross-environment specification](specs/cross-environment-spec.md)
for every task, including resumed and delegated work. These principles and the specification's
design requirements apply continuously, independently of compatibility-suite activation.
Required filesystem permission failures and the specifically authorized backup-directory fallback
retain their existing self-check policy; compatibility does not authorize bypassing them.

Follow the [development compatibility review](contracts/development-contract.md#project-compatibility-review)
and [cross-environment test contract](contracts/cross-environment-contract.md) with its paired
[specification](specs/cross-environment-spec.md). The environment suite is manually triggered and
required before publication, not on every game startup; the ordinary startup permission prerequisite
is a separate operation.

## Computer-use prohibition

Computer-use tools are prohibited for this project. This includes `mcp__cua_repl`,
native desktop control, and browser UI automation through computer-use. Use file
tools, command-line tools, or purpose-built APIs instead. When no permitted
alternative exists, request manual UI interaction from the user. Do not circumvent
this prohibition with another UI automation tool.

## All documentation is written in English

Internal project documentation must use English descriptions and examples. Non-English explanatory prose and illustrative text are prohibited, including localized UI-message examples; describe their meaning and placeholders in English instead. This documentation rule does not change runtime translations or their required language coverage.

Player-facing publishing descriptions and exact official mod-link titles follow the [metadata specification](specs/metadata-spec.md#description-languages-and-official-mod-titles). This scoped exception does not relax internal English documentation or change runtime localization.

Retain a non-English identifier, path, exact diagnostic or source quotation only when its exact spelling is necessary to preserve identifiable evidence. Mark it as a literal source record and explain its role or meaning in English. This narrow evidence exception must not be used for general examples or copied localization strings. Third-party license text remains unchanged. Follow the [documentation standards](documentation-standards.md#language-and-presentation) for presentation and evidence handling.

## Trusted internal execution

All steps and results that do not involve external-device IO are trusted, including memory
operations, pure computation, native in-memory calls and compiler output. GPU uploads, compute/draw
execution, readback and their in-memory inputs and outputs are also trusted. GPU transfers are not
file/network external-device IO validation boundaries. Preserve actual GPU API/driver failures,
asynchronous completion/error states and resource creation/disposal; do not validate the contents
or consistency of trusted GPU inputs/results. Do not add or retain
runtime assertions, input/result verification, finite-value checks, shape/count/range consistency
gates or repeated validation of already accepted owned data for those operations. This is the
project's requested execution/performance policy, not a measured claim about the cause of crashes.
Validate actual file/network input once at its IO boundary; preserve file ownership/containment,
serialized format and dependency checks there, and report actual IO/API/compilation failures.
After data becomes owned internal state, do not revalidate it downstream. Business selection,
algorithmic branches, native game rules, cancellation, locking, scheduling and disposal remain
required behavior, not result validation. Preserve ordinary failure propagation without fabricating
success or adding proactive invariant checks. Independent offline development tests may assert
results; their checks must not enter the mod's execution path. Tools embedded in or invoked by the
runtime follow the runtime rule, regardless of their repository directory.

<a id="repository-game-and-launcher-startup-is-manual"></a>

## Game and launcher startup is manual

Agents must never start Cities: Skylines II or its launcher. This applies to executables, Steam commands and URLs, shortcuts, scripts, UI automation and delegated actions. Agents cannot reliably reproduce a normal player launch. Explicitly decline any request to launch either application. If verification requires a launch or restart, stop at that step immediately and ask the user to perform it manually. Resume verification after the user has started the game. Do not close a player-started instance to facilitate testing.
